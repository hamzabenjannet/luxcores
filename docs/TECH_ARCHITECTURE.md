# Lumen: Technical Architecture

Companion to `GAME_DESIGN.md` v0.9.

Status: draft v0.9. Main change since v0.3: network play moves from lockstep to a server-authoritative model so fog of war can be enforced later (section 13).

---

## 0. Platform roadmap

| Phase | Build | Purpose | Plays against |
|---|---|---|---|
| 1 | HTML + JavaScript + Three.js | MVP, balance tuning, **reference spec** | Bot, hot seat |
| 2 | Godot 4 client + Rust sim core | Full game for PC and web | Godot builds only |
| 3 | Godot only (PC, mobile, web exports) | Single codebase | Godot builds only |
| All | Node.js backend API | Accounts, matchmaking, relay, replays | Serves every client |

The web MVP never plays against Godot builds. Its job is to prove the rules and numbers, then serve as the executable specification for the port.

### 0.1 Why the JS sim is written as a spec

Phase 2 reimplements the sim in Rust. If the JS version follows the portability rules in section 5, a replay recorded in the JS build can be replayed by the Rust core, and both must produce the same state hashes. That turns every playtest replay into a conformance test for the port. It costs little in phase 1: integer math, fixed iteration order, and no JS-only behavior in the sim.

## 1. Principles

1. **The simulation is a pure function**: `state(t+1) = step(state(t), commands(t))`. No DOM, no rendering, no wall clock, no `Math.random`.
2. **A match is fully described by** config + map + seed + ordered command log.
3. **Rendering only reads** sim state.
4. **Every input source emits commands**: touch UI, bot, hot-seat toggle, later the network.
5. **Content is data.** Heroes, abilities, items, buildings and balance numbers live in JSON, so Godot reads the same files.

## 4. Simulation loop

- 20 Hz tick (50 ms). A 10-minute match = 12 000 ticks.
- The client steps from an accumulator and renders at display rate, interpolating between the last two ticks.

### 4.1 Tick pipeline (fixed order)

1. Apply commands for this tick, sorted by `(playerId, seq)`.
2. Economy: collector output into pending pool; settle entries older than 40 ticks; day/night phase.
3. Production: barracks queues (creep groups, items).
4. Hero lifecycle: respawn timers, rotation locks.
5. Recycle channels.
6. Item world: map spawns, ground despawn timers, auto pickup.
7. Behavior: hero orders, creep waypoint following, auto-engage, target acquisition.
8. Movement and collisions.
9. Attacks, ability casts, projectiles.
10. Damage resolution, all simultaneous: shields absorb first, then HP; then procs (stun, knockback); then funnel credit for Energy Grab hits.
11. Timed effects: Haste, Sluggish, shields, ability cooldowns.
12. Entropy.
13. Meltdown check.
14. Deaths and cleanup in ID order; creep kill drops; hero death drops its inventory as a loot bag.
15. Victory check.
16. Every 20 ticks: state hash.

## 5. Determinism and portability rules

These rules keep the JS build deterministic across browsers and make the Rust port able to match it hash for hash.

### 5.1 Numbers

- Lux stored as integer **milli-lux** (1 lux = 1000).
- Positions as integers: 1 tile = 1000 units.
- Angles as integers: 4096 per turn.
- Attack speed as an integer stat (100 = base).
- Plain JS numbers holding integers; exact below 2^53. All division via `idiv(a, b)` = `Math.trunc(a / b)`. Rust uses `i64` and `/`, which also truncates toward zero, so both match.
- No bitwise ops on values that may exceed 32 bits.

### 5.2 Math

- `Math.sin`, `Math.cos`, `Math.atan2` and `Math.exp` are implementation-approximated in the ECMAScript spec. The sim uses a committed integer `SIN_TABLE[4096]` instead.
- `isqrt` for square roots. Squared distances wherever possible.

### 5.3 Randomness

Mulberry32 with its state stored in sim state. It uses only 32-bit integer ops (`Math.imul`, shifts), which map directly to Rust `u32` with `wrapping_mul`.

### 5.4 Ordering and data structures

- Entities in arrays sorted by numeric ID; systems iterate in ID order; ties break on lowest ID.
- No iteration over object keys or `Map`/`Set` inside the sim (their order rules don't exist in the same form in Rust or GDScript).
- Sorting only with explicit comparators on integer keys.

### 5.5 Hash

FNV-1a 32-bit over a canonical byte layout: entities in ID order, fields in a fixed documented order, integers as little-endian 64-bit. The layout is part of the spec, written in `src/sim/hash.js` header comments.

## 6. Physics

Interface unchanged from v0.1:

```js
/** @typedef {Object} PhysicsWorld
 *  @property {(id:number,x:number,z:number,r:number,mass:number,isStatic:boolean)=>void} addBody
 *  @property {(id:number)=>void} removeBody
 *  @property {(id:number,vx:number,vz:number)=>void} setDesiredVelocity
 *  @property {(id:number,ix:number,iz:number)=>void} applyImpulse
 *  @property {()=>void} step
 *  @property {(id:number)=>{x:number,z:number}} getPosition
 *  @property {(x:number,z:number,r:number)=>number[]} queryRadius  // sorted IDs
 */
```

`grid2d.js`: ground-plane simulation, circle colliders for heroes and creeps, tile squares for buildings and blockers, spatial hash with 2-tile cells, 4 overlap-resolution iterations, impulses with linear decay. Projectiles are sim entities with an arrival tick; arcs exist only in rendering.

### 6.1 Pathfinding

- Grid A* on the tile map for hero move orders and for creep segments between waypoints.
- Neighbor order fixed (N, E, S, W, then diagonals) and ties broken on lowest tile index, so paths are identical everywhere.
- Paths recomputed when a building or blocker appears or disappears on the route.
- Map scale: 96 × 112 = 10 752 tiles. A* stays cheap per query, but up to 60 creeps in 1v1 (300 in 5v5) repathing on every building change is not. Two mitigations: repath only groups whose cached path crosses the changed tile, and spread repaths over ticks (at most 8 A* queries per tick, queued in ID order so it stays deterministic).
- A visibility bitset at this size is 10 752 bits = 1 344 bytes per team.
- Curved lanes: each lane is a polyline of control points produced by `mapgen.js` from the templates in `data/mapgen.json`. A creep group without a custom path treats the lane's control points as implicit waypoints, from the nearest point onward, and runs A* between consecutive points.

### 6.2 Visibility groundwork (for post-MVP fog of war)

Cheap now, expensive to retrofit later, so the MVP includes it without enforcing it:

- A `visibility.js` system computes, every 5 ticks, one bitset per team over the tile grid: a tile is visible if any friendly entity's sight radius covers it.
- Each entity gets a derived flag `visibleTo[team]`.
- The client renderer already draws entities through a `isVisibleToViewer(entity)` check that returns `true` in MVP. Turning fog on becomes a config switch for rendering.
- Visibility is part of sim state but excluded from the hash (it's derived data).

What this does **not** do: protect against cheating. Any client holding the full state can reveal everything. Real protection needs the server model in section 13, where hidden entities are never sent.

## 7. Commands

```js
/**
 * @typedef {{tick:number, playerId:number, seq:number, cmd:Command}} CommandEnvelope
 * @typedef {
 *  | {t:'build', building:string, tileX:number, tileZ:number, attack?:string}
 *  | {t:'upgrade', towerId:number, track:'power'|'shell'}
 *  | {t:'recycle', buildingId:number}
 *  | {t:'cancelRecycle', buildingId:number}
 *  | {t:'orderCreeps', barracksId:number, mix:string[]}          // 1 to 5 entries
 *  | {t:'orderItem', barracksId:number, itemId:number}
 *  | {t:'cancelQueue', barracksId:number, index:number}
 *  | {t:'setBarracksPath', barracksId:number, waypoints:number[][]}  // max 10
 *  | {t:'setGroupPath', groupId:number, waypoints:number[][]}        // max 10
 *  | {t:'pickHero', heroId:number, lux:number, barracksId:number}   // own barracks required
 *  | {t:'mergeGroups', intoGroupId:number, fromGroupId:number}
 *  | {t:'splitGroup', groupId:number}
 *  | {t:'heroMove', x:number, z:number}
 *  | {t:'heroAttack', targetId:number}
 *  | {t:'castAbility', slot:0|1|2|3, x?:number, z?:number, targetId?:number}
 *  | {t:'useItem', inventorySlot:number, targetId?:number}
 *  | {t:'pickUp', groundItemId:number}            // single item or loot bag
 * } Command
 */
```

The sim validates every command (ownership, lux, rotation lock, limits, tile validity) and drops invalid ones. The UI runs the same validators for instant feedback.

## 9. Camera (portrait)

- Orthographic camera, isometric angle, map larger than the viewport.
- **Follow mode**: on while the hero is selected; the camera eases toward the hero each frame.
- A one-finger drag pans and turns follow off. Tapping the hero portrait turns it back on.
- Pan clamped to map bounds; pinch zoom clamped to a min and max.
- Picking: ray to the ground plane, then nearest entity via the sim's `queryRadius`.

## 11. Testing

| Test | How |
|---|---|
| Determinism | Run each golden replay twice in Node, compare all hashes |
| Cross-browser | A test page runs golden replays in Chrome Android and iOS Safari, compares final hashes to Node |
| Spec stability | CI fails when a golden replay's hash changes without a `specVersion` bump |
| Rules | Unit tests per rule: rotation lock, 2 s buffer, recycle 60%, meltdown at 120 s, Energy Boost refused on Core |
| Bot soak | Bot vs bot, 1000 seeds, headless; no crash, no non-integer values, matches end |
| Port conformance (phase 2) | The Rust core replays the JS golden replays and must produce identical hashes |

## 12. Phase 2 notes (Godot)

- **Sim core in Rust**, exposed to Godot 4 through godot-rust (gdext). Godot handles rendering, input, UI and audio; Rust handles the sim.
- Same `data/*.json` files and same `.glb` assets.
- Godot exports to PC, mobile and web from one project. Support for GDExtension in Godot's web export, and gdext's WASM support, must be verified against the Godot and gdext versions current at port time; if either is missing, the fallback is a GDScript sim validated by the same golden replays.
- Godot builds play each other cross-platform (PC vs mobile). The integer-only rules in section 5 make that safe.

## 13. Backend (Node.js, later)

One API for every client:

- Accounts and profiles (future: starting Core buffs from account level).
- Matchmaking for 1v1 and 5v5.
- Match server (section 13.1).
- Replay storage.

### 13.1 Server-authoritative model (replaces v0.1 lockstep)

Lockstep sends every command to every client and each client simulates the full world, so a modified client can always see through fog. Fog of war therefore needs the server to own the simulation.

| | Lockstep (v0.1 plan) | Server-authoritative (v0.4 plan) |
|---|---|---|
| Who simulates | Every client | Server only (clients predict their own hero) |
| What clients receive | All commands | Per-player snapshots: only entities that player's team can see |
| Fog of war | Cosmetic, bypassable | Enforced |
| Bandwidth | Tiny (commands only) | Higher (state deltas) |
| Server cost | Relay only | One sim per match |
| Lag handling | Everyone stalls | Others unaffected; the lagging player sees late updates |

Design:

1. Clients send commands, stamped with their local tick.
2. The server runs the sim at 20 Hz, applies commands on arrival, and every 2 ticks (10 Hz) sends each player a **delta snapshot** filtered by that team's visibility bitset.
3. Clients render remote entities about 100 ms in the past and interpolate between snapshots.
4. The player's own hero is predicted locally (movement only) and corrected when the server snapshot disagrees.
5. Reconnect: the server sends a full filtered snapshot; no fast-forward needed.
6. Replays: the server keeps seed + command log, so the determinism work from phase 1 still pays off (replays, debugging, port conformance).

What stays useful from phase 1: the deterministic sim, the command schema, the hash, the golden replays. What changes: clients stop simulating the whole world in network play.

Server sim language: phase 2 uses the Rust core; Node loads it as WASM or as a native addon, so the server and Godot clients run identical rules.

### 13.2 Groundwork in phase 1 (low cost)

- Keep `isVisibleToViewer()` in the renderer (section 6.2).
- Keep the renderer reading state through a `WorldView` interface (entity list + lookups). In MVP it wraps the local sim; later it wraps the snapshot buffer. Nothing in `client/` touches sim internals directly.
- Nothing else in phase 1 depends on networking.
